# Git flow

Solo-dev flow with **snapshot releases**: master never receives merges, only
generated one-commit-per-version snapshots of develop. Back-merges are
impossible to need, by construction.

## Branches

| Branch | Role |
|---|---|
| `develop` | Default branch. All real history lives here. Feature branches merge back into it. |
| `master` | Release line. Linear, exactly one commit per version, each tagged `vX.Y.Z`. **Never commit, merge, or branch-off here.** Generated by `make release`. |
| `feature/*` | Branched from develop, merged back to develop. Delete after merge. |
| `old-master` | Frozen archive of the pre-2026-06-11 master (squash-merge era). Safe to delete eventually. |

## Daily work

```
git checkout develop
git checkout -b feature/my-thing
# ...work, commit...
git checkout develop && git merge feature/my-thing   # or open a PR to develop
git branch -d feature/my-thing
```

## Cutting a release

During development, log notable changes under a `## [Unreleased]` section at
the top of `CHANGELOG.md` as they merge. Then:

1. On develop: bump `"version"` in `package.json`, commit.
2. Run:

```
make release
```

The script (`scripts/release.sh`) refuses to run unless: you're on develop, the
tree is clean, the `package.json` version is **strictly higher** than the
latest `v*` tag, local master == origin/master, and `## [Unreleased]` exists
with content. Then it:

- renames `## [Unreleased]` to `## [X.Y.Z] — date`, inserts the GitHub compare
  link, and commits that on develop;
- creates one commit on master whose **tree is develop's tree, verbatim**
  (`git commit-tree develop^{tree} -p master`), with the changelog section as
  the commit message — no merge, no conflict possible;
- tags it `vX.Y.Z`;
- pushes develop, master, and the tag.

## Packaging the VSIX

`vsce` packages whatever is checked out, so ship from the tag:

```
git checkout vX.Y.Z
make package          # → hydragit-X.Y.Z.vsix
git checkout develop
```

## Why no back-merges

A snapshot commit *contains nothing develop lacks* — its tree IS develop's
tree at release time. master can therefore never be "ahead" in content, and
there is nothing to merge back. The old pain (squash-merging develop→master,
then `-s ours` back-merges to realign) is gone.

The trade-off: master's commits are synthetic, not reachable from develop's
history, so `git log master..develop` is not meaningful. Compare releases by
tag instead: `git diff v0.2.4 v0.2.5`, `git log master` (reads like the
changelog).

## Rules

- Version bumps happen **on develop only**. Never touch master directly —
  that is exactly what caused the old divergence.
- Keep `## [Unreleased]` in `CHANGELOG.md` up to date as features merge —
  `make release` turns it into the version section automatically.
- Tags are published facts: never re-point a pushed tag (the 2026-06-11
  retro-tagging was a one-time history cleanup). If a release is broken,
  ship a new patch version instead.
- Other clones: a plain `git fetch` won't update moved tags from the 2026-06-11
  cleanup; run `git fetch origin --tags --force` once per clone.
